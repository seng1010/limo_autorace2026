## 주차 인계 순서

1. M1 완료 후 M4에 진입하면 매니저는 주차 노드를 대기 상태로 실행하고 **차선 명령**을 계속 선택한다. 이전 M1 정지선 거리 메시지와 이전 주차 명령의 수신 기록은 폐기하되, 아래 네 선 구분에 사용하는 선의 odom 위치는 유지한다.
2. 정상 M1→M4 주행에서는 횡단보도 끝선을 통과하고 **그 다음 주차 시작선**이 확인되어야 정지 접근을 시작한다. 단독 `start_mission=M4`는 기존처럼 처음 관측하는 정지선을 사용한다. 선택된 선의 거리가 `m4_line_arm_distance_m` 이내일 때 횡단보도 M3와 동일한 `StopApproachController`로 속도를 제한한다. 속도와 각속도를 같은 비율로 줄여 차선 명령의 조향 곡률을 유지한다. 임의로 조향을 0으로 만들지 않는다.
3. 앞바퀴 축 기준 거리 `m4_stop_offset_m`에 도달하면 정지 명령을 유지한다. 신선한 odom의 속도가 `full_stop_speed` 이하로 주차 전용 `m4_full_stop_sec=0.5`초 동안 연속 유지되어야 시작 신호를 보낸다. 움직임·odom 만료·ESTOP 뒤에는 다시 센다. 명령 속도 0만으로 정지를 확정하지 않는다. M1/M3의 `full_stop_sec=0.3`은 그대로다.
4. 주차 노드는 자체 직진 접근을 건너뛰고 기존 `settle_sec` 대기 → `forward` → `turn` → `enter`를 실행한다. 이 단계들의 파라미터와 아커만 변환식은 그대로다.
5. 주차 `DONE`은 `mission/parking/state=complete`로 매니저에 전달한다. 매니저는 최종 M4를 유지하고 정지한다. 표지판을 먼저/늦게 보는 것이 주차 시퀀스를 직접 시작하거나 재시작하지 않는다.

사용자가 지정한 시작 자세는 **차로 좌우 중앙 부근, 앞바퀴 축이 정지선 가까운 가장자리 부근**이다. 좌우 중앙 접근은 기존 차선 주행에 맡긴다. 매니저가 실제 중앙 정렬이나 바퀴 조향각을 측정·확정하는 것은 아니다.

| 설정 | 초기값 | 의미 |
|---|---:|---|
| `m4_line_arm_distance_m` | 0.80 m | M4 정지선 접근 판단 시작 |
| `approach_start_m` | 0.50 m | M3와 공유하는 감속 시작 거리 |
| `m4_stop_offset_m` | 0.01 m | 정지 명령을 내기 시작할 앞바퀴 기준 남은 거리 |
| `full_stop_speed` | 0.01 m/s | 실측 정지 판단 기준 |
| `m4_full_stop_sec` | 0.5 s | 주차 시작 허가 전 정지 확인 지속 시간 |
| `m4_skip_crosswalk_end` | true | 정상 M1 출발 후 첫 새 선은 횡단보도 끝으로 제외하고 다음 선을 주차선으로 선택 |

0.01 m는 M3 공용 정지 보정값과 같은 초기값이지 실측 보장값이 아니다. 정지선 검출 보정, 제동거리, 낮은 속도에서의 실제 구동 여부를 LIMO에서 확인해야 한다. 접근 최저속도 `approach_creep_speed=0.06`은 이번에 바꾸지 않았다. 이 값에서 실차가 움직이지 않는다면 정지선 전에 대기할 수 있으므로 정지선 정확도와 함께 별도 튜닝한다.

위 0.5초는 **주차 시작 허가 전** 시간이다. 허가를 받은 주차 노드 내부의 기존 `STOP_WAIT`/`settle_sec`는 별도로 유지하므로 실제 바퀴가 움직이기까지는 그 대기 시간이 더해진다.

## 명령 소유권과 중단

- M4 접근·정지 확인: 매니저가 차선 제안을 선택한다.
- 주차 시퀀스: 매니저가 주차 제안을 선택한다. 차선·3차선·콘 검출/경로 생성 코드는 수정하지 않았다.
- 시작 허가는 20 Hz로 반복 발행한다. 노드가 늦게 실행되어도 단발 시작 신호를 놓치지 않는다.
- managed 주차는 시작 허가가 0.5초 넘게 끊기거나, 현재 미션 알림이 M4가 아니거나 1.5초 넘게 끊기면 정지하고 타이머 진행을 일시 중단한다. 새 허가 시 남은 단계 시간을 이어간다.
- `ESTOP`은 미션별 정지와 별도로 유지하며 `NEXT`, 완료 이벤트, M8 즉시 발행 콜백으로 해제되지 않는다. `ESTOP_CLEAR` 후에는 이전 명령을 버리고 새 제안을 기다린다. 주차 단계 자체를 처음부터 재시작하지 않는다.
- 기존 단독 `parking_line_detection.py` 실행의 `go`/Enter, `start_delay_sec`, 자체 접근 방식은 유지한다. managed 실행에서는 접근/시작 권한을 매니저가 소유한다.

## 같은 브랜치의 매니저 수정

- 신호등 상태 수신이 `traffic_state_timeout_sec=0.5`초 넘게 끊기면 마지막 녹색을 새 출발 판단에 재사용하지 않는다. 이미 교차로를 통과 중인 M1의 기존 상태 판단은 바꾸지 않았다.
- `m1_max_wait_sec=0`으로 기본값을 변경했다. 적색/미확인 상태에서 30초만 지나 자동 출발하던 우회는 기본 비활성이다. 양수로 명시하면 기존 우회가 재활성화된다.
- M1/M3에서 odom이 없거나 만료되면 명령값으로 완전정지를 추정하지 않고 대기한다. 관측 공백 뒤 정지 확인 시간을 새로 센다.
- M1/M3 완료 직후 같은 타이머 실행에서 이전 명령이 전환 정지 명령을 덮어쓰지 않는다.
- 전체 주행의 매니저 설정에 M8 단독 launch와 동일한 입구 설정(55 cm 사전검사, 45 cm 보호접근)을 연결했다. M2 진입 즉시 콘 제어를 선택하는 것은 아니며, 콘 내부·충돌검사·출구 조건은 그대로다.

## 11/16 21:42:31 bag 재현 후 수정

`bag_full_20261116_214231`에서 M8 종료는 43.15초였다. 53.49초에 M1 시작 후 약 2m를 이동하자 `skipped`가 발생했고, 매니저가 이를 성공과 동일하게 처리해 M4를 실행했다. 따라서 서행 시작선에 주차 정지를 수행한 것이며 신호등 정지선 자체를 잘못 선택한 현상이 아니었다.

- 매니저의 M1 접근 거리 제한은 항상 비활성이다. `m1_max_approach_distance_m`은 이전 설정 파일 호환을 위해 선언만 남겼으며 양수를 주면 경고하고 무시한다. 예외적으로 `skipped` 결과가 들어와도 M4로 전환하지 않고 정지한다. M3 정책은 바꾸지 않는다.
- 첫 선은 기존 위치 기반 중복 제거로 한 번 세고 `m1_slow_speed=0.15`로 서행한다. `m1_skip_lines=1`을 유지한다.
- 두 번째 선에서는 `m1_trigger=light_or_line`으로 신호 미인식 때도 정지한다. `m1_stop_on_green_arrival=true`이므로 녹색 도착도 예외 없이 odom 정지 0.3초를 확인한다. 출발에는 유효한 녹색이 필요하며 기본 `m1_max_wait_sec=0`으로 시간만의 출발은 허용하지 않는다. 이후 기존 0.5m 완료 거리로 M4에 인계한다.
- M1 디버그에 `lines=N`을 추가해 첫 선/두 번째 선 판단을 기록한다. 검출기·차선 조향·정지선 거리 보정은 수정하지 않는다.
- M2 진입 때 콘 노드를 **제안용으로 미리 실행**한다. 기존에는 부분 입구선 확인 후 프로세스를 시작해서 0.8초인 관측 근거가 노드 준비 전에 만료될 수 있었다. `watch_entry`의 차선 소유권과 기존 입구 확인·명령 신선도·충돌검사는 그대로다. `auto_start_mission_nodes=false`에서는 외부 launch의 노드를 추가 실행하지 않는다. 이미 시작된 프로세스는 기존 중복 방지로 재사용한다. 콘 노드의 10Hz LiDAR 계산은 M2부터 일찍 수행되므로 실제 CPU 부하는 확인해야 한다.

재현 도구(ROS 설치 없이 테스트 환경의 Python으로 실행):

**재생 한계:** 수정한 명령에 따라 차량이 실제 이동하는 폐루프 실험이 아니다. 원래 주차 시퀀스/수동 조종으로 이동한 odom이 그대로 들어가므로 57.95초 등의 시각과 실제 정지 위치를 새 주행의 예측값으로 보지 않는다. 정지 후 녹색 출발→M4→주차 완료는 별도 연속 콜백 시뮬레이션으로 검증한다. 첫 기록(`213838`)은 중복 teleop 실행에 따른 카메라 문제를 사용자가 확인했으므로 회귀 기준에서 제외했다.

## 11/17 보완: 횡단보도 끝선과 주차 시작선 구분

사용자가 확인한 콘 이후 배치는 아래와 같다. 횡단보도 내부 줄무늬 수를 세는 것이 아니라 기존 정지선 검출기가 전달하는 구간 경계선을 구분한다.

| 순서 | 선의 의미 | 매니저 동작 |
|---|---|---|
| 1 | 서행 시작선 | 기존 M1 서행 |
| 2 | 횡단보도 시작선 | 기존 신호 정지·정지 확인·녹색 출발 |
| 3 | 횡단보도 끝선 | 차선 주행으로 통과, 주차 시작 금지 |
| 4 | 주차 시작선 | 기존 정지 접근 → odom 정지 0.5초 → 주차 허가 |

기존에는 M1 출발 후 0.5m에서 M4가 시작되고, M4의 첫 새 거리 메시지를 곧바로 주차 대상으로 사용했다. `bag_full_20261116_234026`에서는 이 대상이 세 번째 선이었다. 단순히 M1 완료 거리를 늘리면 배치·검출 위치에 따라 다시 엇갈리므로, 완료 거리는 유지하고 선의 역할을 보존한다.

- M1 출발 순간부터 `LinePassDetector`를 별도로 사용한다. 신호 정지선 위치를 초기값으로 넣고 `odom 누적거리 + 앞바퀴 기준 선 거리`가 일관된 새 선을 기억한다. M4에 넘어오기 전에 세 번째 선이 관측되어도 다시 주차선으로 세지 않는다.
- 기존 선 구분 기준인 2개 관측, 위치 일치 12cm, 이전 선 이후 최소 30cm를 재사용한다. 매니저 타이머가 같은 메시지를 여러 번 읽는 것은 추가 관측으로 세지 않는다. 후진·odom 만료 중에는 새 선을 채택하지 않는다.
- 세 번째 선을 앞바퀴가 2cm 이상 지난 뒤, 그 다음 선의 현재 관측 위치가 기록된 주차선 위치와 일치할 때만 기존 M4 정지 접근에 연결한다. 그전에는 기존 차선 제안을 유지한다. 정지선 검출기, 일반 차선 조향, 주차 시퀀스 및 속도 설정은 변경하지 않았다.
- `start_mission=M4` 단독 시험과 `m4_skip_crosswalk_end=false`는 기존 첫 선 접근 동작이다. 정상 전체 주행은 기본값 true를 사용한다. 운영자가 강제로 NEXT를 보내는 시험은 정상 신호 출발 경로와 같다고 보지 않는다.

### 기록 재생 및 검증 한계

실제 매니저 콜백을 같은 기록에 재생한 결과, 변경 전 주차 시작은 **96.820초**로 원래 기록과 일치했다. 변경 후 세 번째 선의 위치는 약 **6.504m(해당 재생의 odom 누적거리)**로 기억하고, 이 선에서는 주차 시작 신호를 내지 않았다. 95.5–99.0초의 70개 제어 주기에서 변경 전 58개 정지 명령, 변경 후 0개 정지 명령이 나왔으며 변경 후에는 기록된 차선 제안이 선택됐다.

원본 영상·odom은 그대로이므로 이는 명령 선택 비교이지 새로운 주행 성공 영상이 아니다. 사용자가 약 99초부터 간헐적 수동 조종을 했다고 확인했고, 이 기록에는 수정된 방식으로 네 번째 선에 도달해 주차하는 실차 결과가 없다. 네 번째 선 접근·정지·주차 완료 연결은 별도의 연속 콜백 시뮬레이션으로 확인했다. 세 번째 선을 완전히 놓치거나 검출기가 가짜 선을 출력하면 선 순서가 틀어질 수 있으므로, 새 시험에서 아래 로그와 영상의 대응을 확인한다.

- `횡단보도 끝선 확인: 통과 대상이며 주차 시작 금지`
- `parking_approach source=lane waiting_parking_start`
- `횡단보도 끝선 다음 주차 시작선 확인`
- `M4 정지선 앞 완전정지 확인; 기존 주차 시퀀스 시작`

회귀 테스트는 M1 중 미리 본 끝선의 보존, 반복 메시지·후진 관측 제외, 기존 M4 단독 시험, 정지 확인 중 odom 유실/움직임, M2→M8→M1→끝선 통과→M4 주차 완료를 포함한다. 전체 Python 테스트 340개 통과. 재생·비교 영상 도구는 작업 폴더의 `m8_offline/verify_four_line_parking.py`이며 ROS 하드웨어로 명령을 발행하지 않는다.
