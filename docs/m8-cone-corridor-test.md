# M8 콘 주행 통합본 — 구현, 검증, 배포

2026-11-15. 배포 브랜치: `feature/m8-cone-corridor`.

## 결론

긴 좌우 경계선/중앙경로와 여러 단계 복구를 **관측된 콘 사이 통과점 + 20 cm 진행 원호**로 대체했다. 차선 노드는 계속 실행한다. M8 진입이 허용된 상태에서 콘 명령을 받으면 매니저가 즉시 전달한다. 콘 내부에서 차선 명령을 섞지 않는다.

실차 성공 보고서는 아니다. bag의 고정 시점에 새 판단을 넣는 재생과 별도의 단순 폐루프 시뮬레이션을 구분했다. 명령 발생률을 통과 확률로 해석하지 않는다. 개발 Mac에서는 ROS2/Jetson 실행을 검증하지 못했다.

## 없앤 것과 남긴 것

- 제거: 전체 두 줄 완성이 필요한 경로 구성, 여러 단계 대체 원호, 동일 원호 충돌검사의 반복, 공용 YAML의 M8 설정, 매니저 안에 쌓인 콘 전용 분기.
- 유지: 최소 구동속도 0.10 m/s, 센서 유효성, 차체·콘 받침 충돌 검사, 사용자 ESTOP, 명령 타임스탬프, 출구에서 실제 관측 차선 확인.
- 통합: ROS와 외부 재생이 동일한 `Planner.update`를 사용한다.
- 짧은 유실: 명령을 맹목적으로 유지하지 않는다. 최근 관측 통과점/주변 점을 odom으로 좌표 변환하여 최대 0.5초·0.10 m 재사용하고, 현재 스캔으로 매번 진행 방향과 충돌을 확인한다. 예측만으로 기억 시간을 연장하지 않는다.
- `lost/emergency_stop` 문자열이 공통 `_blocked`를 덮어쓰지 않는다. 속도·각속도·스캔 시간이 묶인 명령을 읽고, 사용자 ESTOP는 별도로 유지한다.

## 계획기

1. beam 순서/거리 변화로 클러스터링한다. 충돌검사에는 클러스터가 아닌 원시 점도 남긴다.
2. 가까운 최대 24개 클러스터에서 횡방향 콘 쌍을 찾는다. 유효 폭, 가운데 다른 장애물, 진행 방향을 확인한다. 완성된 두 줄 전체는 요구하지 않는다.
3. 거리·방향·통과점 도착 방향으로 점수화한다. 단순 최근접 쌍의 대각선 오연결을 줄이고 상위 8개 후보를 평가한다.
4. 아커만 곡률 범위에서 20 cm 진행 원호를 샘플링한다. 차체 직사각형 모서리까지 원시 점과 충돌하지 않고 목표에 가까워지는 원호를 선택한다.
5. 같은 곡률의 충돌 결과는 스캔마다 한 번만 계산한다. 안전한 두 스캔 뒤 0.10 m/s, 장애물/스캔 유실이면 0을 발행한다.
6. odom이 없거나 오래되면 현재 스캔의 새 쌍만 사용한다. 후진, odom 점프, 시간 역행 시 기억을 지운다.

멀리까지 완벽한 경로가 나오길 기다리지 않고 짧게 진행해 재관측한다. 콘이 안 보이거나 차체/진행 원호가 막혔는데 강제 출발시키는 방식은 아니다.

## 제어권과 기존 주행

| 단계 | 동작 |
|---|---|
| 평상시 M2, M8 비활성 | 기존 race 주행 |
| ARM_M8/M2_DONE/NEXT 또는 지정 거리로 준비 | 차선 인식 유지, LiDAR 검사한 접근 차선 명령 |
| 준비 상태에서 콘 통과점 확보 | 첫 정지선 통과를 추가로 기다리지 않고 M8 콘 제어 |
| 콘 내부 | 콘 명령만 사용, 없거나 오래되거나 0이면 정지 |
| 서로 다른 출구 정지선 또는 누적 콘·odom 통과 확인 | `exit_prepare`: 콘 제어를 유지하고 차선 연결 경로 병행 검사 |
| 준비 상태에서 안전한 새 차선 명령 확보 | `exit_lane`: 차선으로 인계, 이후 차선 명령 유실은 정지 |
| 출구 선 통과 또는 콘 통과 확인 + 차선 진행 거리 충족 | 기존 순서의 다음 미션 |

`Planner → mission/cone/safe_cmd_vel(TwistStamped) → M8Control → mission_manager_node /cmd_vel → 기존 cmdvel_to_ackermann → /limo/ack_cmd`

`mission/cone/cmd_vel`은 호환/관측용이다. 매니저는 시간이 포함된 safe_cmd_vel을 읽는다. 상태 문자열과 명령의 수신 순서가 달라 출발이 막히던 구조를 제거했다.

`angular.z = v × curvature`이다. 기존 race bridge/보정 배율을 콘에서 또 곱하지 않는다. 안쪽 바퀴 목표각과 /limo/ack_cmd의 보정된 중심각 명령은 서로 다른 값이며, 실제 조향 센서 측정값도 아니다. 예전 limo_base의 11도 제한 경로로 바꾸지 않는다.

### 정지선과 전체 주행의 전제

첫 선은 콘 진입의 필수 조건이 아니지만 **두 번째 선을 구별하는 기준**이다. 전체 인계 시험은 첫 정지선이 보이는 입구에서 시작한다. 콘 한가운데에서 `start:=M8`로 시작하면 콘 주행은 가능해도 첫 선 기준이 없어 자동 출구 인계가 완료되지 않을 수 있다.

전체 대회에서는 기본 설정대로 팀의 구간 판단이 M2에서 ARM_M8/M2_DONE을 전달한다. M8 시험 launch의 `start:=M2 motion:=true`에서는 아래 세 단계를 거친다.

1. `watch_entry`: 입구 선만 관측하고 기존 race 차선 명령과 속도 제한을 그대로 사용한다.
2. `preflight`: 앞 차축 기준 `entry_precheck_m`(기본 0.55m) 이내에서 입구 선이 일관되게 3회 관측되면 선의 위치를 odom에 고정하고, 현재 LiDAR와 차선으로 기존 20cm 접근 검사를 미리 실행한다. 주행 명령은 아직 race 쪽이다.
3. `approach`: 저장한 선까지 odom 기준 `entry_near_m`(기본 0.45m) 이내이거나, 현재 차선 조향으로 전방 20~35cm를 내다봤을 때 차체·콘 받침 모델 여유가 추가 여유 기준+2cm(현재 기본 4cm) 미만이면 보호 접근을 시작한다. 이 원거리 판단은 제어권 전환에만 사용하고 주행 승인은 기존 20cm 검사와 최신 명령에 한한다. LiDAR 경보보다 오래된 주행 제안은 재사용하지 않는다. 기존 0.10 m/s 제한, 콘 인계 직후 계획기 초기화, 출구 조건은 그대로다.

M2의 입구 검출은 수평선 판정을 유지하고, 실패 시 카메라 중앙 양쪽에 충분히 보이는 비스듬한 흰 선을 보조 검출한다. 선의 기울기를 고려해 카메라 중앙에서의 하단 행으로 거리를 계산한다. 중앙을 충분히 덮지 못하는 부분 입구선은 아래의 별도 결합 판단을 사용한다. odom이 -0.02 m/s 미만인 동안에는 새 입구 확정과 콘 제어권 인계를 허용하지 않는다. 이미 사전 검사/보호 접근 중이면 정지 명령을 내고, 후진 종료 이후의 새 검증 명령을 기다린다.

입구 선을 못 보면 자동 검사가 켜지지 않는다. 첫 실차 시험은 선이 보이는 접근 구간에서 진행하고 전환되지 않으면 차량을 정지한다. `motion:=false`는 기존 즉시 접근 가드를 유지한다. 튜닝은 `0.15 <= entry_near_m <= entry_precheck_m <= 0.60` 범위에서 한다.

### 부분 입구선 + 실행 가능한 콘 통로 결합 (2026-11-15)

**수정 이유:** `225830`에서는 입구 흰 테이프가 영상 오른쪽에만 보인다. 기존 검출은 영상 중앙 양쪽 지지를 요구하므로 선을 놓쳤고, 이미 유효한 콘 명령이 있어도 `watch_entry`에 남아 차선으로 지나쳤다. `230117`은 가까운 선 일부가 영상 하단에서 잘려 같은 문제가 생겼다. 일반 정지선 검출 전체를 느슨하게 하지 않고 M2 입구에만 대안을 추가했다.

- 기존 수평/비스듬한 전폭 검출을 먼저 적용한다. 실패한 경우에만 부분 흰 테이프의 길이·두께·기울기·면적·인접 노란 차선 접점을 검사한다. 한쪽에만 보이는 선과 중앙을 포함한 하단 잘림을 구별하며, 바깥 흰 테두리만으로는 인정하지 않는다. 흰색 마스크와 윤곽은 한 번 계산해 공유한다.
- 부분 관측은 `/mission/cone/partial_entry_line` (`PointStamped`, `front_axle`, `point.x`=추정 앞 차축 거리, 음수=미검출)로 따로 보낸다. 기존 전폭 거리 토픽이나 출구 검출을 가짜 양성으로 바꾸지 않는다. 보정표가 없거나 카메라 데이터가 오래되면 부분 인계를 허용하지 않는다.
- M2 `watch_entry`에서 서로 다른 카메라 프레임 3회의 odom 기준 선 위치가 일치해야 한다. 프레임 사이 최대 0.25초, 위치 차이 8cm 기준은 기존 정지선 확인 함수를 공유한다. 확인된 관측은 최대 0.8초·20cm만 유효하며 후진하면 폐기한다. 후진 종료 전 찍힌 지연 영상도 새 확인에 사용하지 않는다.
- **부분선 확인만으로 제어권을 가져오지 않는다.** 기존 콘 계획기/안전검사를 통과한 0.10m/s 이상 명령이 0.25초 이내로 신선할 때만 즉시 기존 M8 인계 절차를 사용한다. 그 전까지 race 차선 주행을 유지한다. 정지·최소 구동속도 미만·오래된 콘 제안, odom 유실, 사용자 ESTOP에서는 새 인계가 되지 않는다.
- 기존 전폭 선의 55cm 사전검사 → 45cm/전방 여유 보호접근은 그대로다. 부분 선의 중앙 투영 거리는 정확한 실측거리로 간주하지 않으며 45cm 트리거 대신 입구 관측과 콘 명령을 결합한다. 추정 입구 위치는 기존의 서로 다른 출구선 구별용 기준점으로만 전달한다.
- 콘 내부 계획기, 20cm 안전검사, 30~40cm 선행 점수, 인계 직후 초기화, 후진/전진 복구, 출구 검출·인계·대기 조건, 일반 차선 제어, 아커만 bridge는 수정하지 않았다. 남은 좁은 통로 정지/출구 대기는 이번 수정 대상이 아니다.

세 bag 전체 카메라 **6,221프레임**에서 기존 전폭/수평 전용/출구 검출 출력은 수정 전과 모두 동일했다. 부분 관측을 넣지 않는 비교에서는 세 bag의 M2 명령 결과가 수정 전과 완전히 동일했고, 부분 관측을 넣은 경우도 새 인계 이전 명령은 동일했다. 단위·가짜 ROS 연결 테스트 **211개 통과**: 부분선 단독/콘 명령 단독, 후진·지연 영상, 관측 만료, 오래된 odom, 최소속도 미달, 비활성 모션, 다른 미션, 출구 인계를 포함한다.

부분 후보 포함 검출 비용은 개발 Mac p95 약 1.5~2.1ms였으며 Jetson 실측이나 ROS 전체 지연 수치가 아니다. GPU 추론은 추가하지 않았다. 검증 영상은 새 인계 시점에서 정지 화면으로 끝낸다. 인계 후 실제 궤적이 달라지므로 기존 bag으로 완주 성공률이나 이후 충돌 여부를 보장하지 않는다. LIMO에서 첫 bag과 같은 왼쪽 치우침·우회전 직후 진입, 가까운 입구에서 정지 출발, 후진 중 미인계를 다시 확인한다. 새 관측 토픽은 기본 bag 녹화 목록에 포함했다.

## 실측 받침 보정·전진 조향 탐색·통로 방향 정렬 (2026-11-16)

**수정 이유:** `235135`, `235301`의 부분 입구선 인계는 실제로 성공했으나 콘 내부에서 `path_blocked`가 반복됐다. 종전에는 라이다 단면에서 받침까지 4.5cm, 그 밖의 여유 2.5cm를 더해 원시 점과 예측 차체 사이 7cm를 요구했다. 사용자가 받침의 **한쪽 돌출은 3cm 미만**임을 확인하고 추가 여유 1.5cm를 지정했으므로, 받침 보정 3cm + 여유 1.5cm = 4.5cm로 맞췄다. 이는 실제 주행 오차를 포함한 안전성 보장이 아니므로 첫 실차 시험에서는 사람이 없는 통로에서 리모컨 정지 준비가 필요하다.

- `Params`, 노드 기본값, M8 YAML을 모두 동일하게 바꿨다. 사용자 확인에 따라 **출구 충돌검사에도 같은 거리 보정**을 적용하지만 출구 검출·인계·완료·대기 상태 로직은 변경하지 않았다.
- 기존 11개 균등 곡률 + 통과점 추종 곡률에, 통과점 방향 정렬을 반영한 중간 곡률 후보를 추가했다. 기본 탐색으로 실행 가능한 후보가 하나도 없을 때만 81개 균등 곡률까지 세분화한다. 최대 8개 통로 쌍에서 곡률별 충돌/관측 결과를 공유하므로 1스캔의 서로 다른 검사 수는 최대 97개(81+16)다. GPU·학습 모델·새 제어 상태는 추가하지 않았다.
- 통과점 위치에만 맞추는 대신 콘 쌍의 법선(통로 진행 방향)에 대해 **20cm 이동 뒤 차량 방향 오차가 얼마나 감소하는지**를 점수화한다. 먼 쌍은 가중치를 줄이고 가까워질수록 정렬을 중시한다. 목표 곡률과의 편차는 제곱 비용으로 바꿔 작은 중간 조향 보정을 허용한다. 정렬되면 방향 비용이 조향을 풀도록 작용하며 최대조향 고정/우회전 강제/검출 안정 타이머는 없다.
- 20cm 전진 궤적, 원시 점 충돌 검사, 진행 방향의 유효 라이다 관측, 목표로 7cm 이상 접근, 기존 곡률 상한, 0.10m/s 속도, 두 번 연속 유효 관측 후 재개를 유지했다. 38cm 앞 장애물 여유는 기존과 같이 점수에만 사용한다.
- 후진 및 짧은 전진 복구를 추가하지 않았다. 일반 race 차선/bridge, 매니저 제어권 로직, 인계 직후 초기화, 정지선 관측 코드는 변경하지 않았다. 새 콘 제안이 더 일찍 유효해지면 동일한 인계 조건의 충족 시점은 달라질 수 있다.
- `/mission/cone/timing`에 `search_stage`(coarse/refined), `candidate_count`를 추가했다. 유효 통로가 없거나 현재 차체가 이미 막힌 경우에는 탐색 전 반환하므로 stage는 null, count는 0이다.

검증은 `e8a994e`와 비교했다. 원본 bag을 바꾸지 않고 동일한 기록 위치·스캔·odom·제어 단계를 사용해 기존/거리 보정만/전체 수정의 실제 `Planner.update`와 연속 관측 재개 조건을 실행했다. **제안 수는 통과 성공률이 아니며 새 명령 이후의 실제 궤적을 예측하지 않는다.** 기록의 수동 조작도 그대로 남아 있으므로 control_mode=1 구간을 별도로 집계했다.

control_mode=1에 한정하면 첫 bag은 273개 중 173→271, 둘째는 266개 중 189→266개다. 정지 개선의 주효과는 받침 보정이다. 이 두 bag의 cone 단계에서는 전체 수정의 기본 탐색만으로 충분하여 세분화 탐색은 호출되지 않았다. 81개 재탐색은 좁은 유효 곡률 대역을 만든 별도 테스트로 확인했다. 같은 통로를 선택하고 양쪽 제안 모두 진행 가능한 프레임에서 예측 방향 오차 평균은 각각 17.35→16.37도(210개), 17.84→17.01도(254개)였다. 실측 차량 방향 개선 수치가 아니다.

모든 새 진행 제안의 원시 점과 20cm 예측 차체 사이 거리는 4.5cm 이상이었다. 개발 Mac 코어 p95는 첫 bag 15.1→19.0ms, 둘째 14.0→20.4ms였다(ROS/카메라/Jetson 실행 비용 제외). Jetson의 기존 `plan_ms`, `arrival_age_ms`와 새 탐색 카운터로 추가 확인해야 한다. ROS 결과 유효시간 제한은 그대로다.

회귀 테스트 216개 통과. 좁은 대역의 세분화 탐색·중복 검사 방지·기본 탐색의 연산 상한·좌우 대칭 정렬·정렬 후 조향 해제·최대조향이 막힐 때 중간 조향·관측 누락 시 정지·기존 후진/출구 조건을 포함했다. 기존 단순 운동학 시뮬레이션 24개는 전후 모두 완료, 충돌 0회였고 모델상 받침 최소 간격은 4.39→5.12cm였다. 실제 완주 확률/조향 응답 보장은 아니다.

외부 검증 코드는 `m8_offline/verify_forward_alignment.py`, 비교 영상 코드는 `m8_offline/render_forward_alignment.py`에 두었다(이 저장소 밖). 영상의 카메라/odom은 녹화 당시 값이고, 좌우 패널은 해당 위치에서 계산한 기존/수정 콘 **제안**이다. exit_lane 단계에서는 콘 제안을 표시해도 매니저가 선택하지 않는다는 문구를 표시한다. 기존 출구 대기를 해결했다고 해석하면 안 된다.

실차 확인 순서: 같은 부분 입구선 접근 → 콘 내부 0.10m/s 연속 진행 여부 → 최대각 대신 중간 조향으로 통과하는 구간 → 실제 콘 받침 최소 간격 → 제어 지연 → 기존 출구 전환/대기. 후진이나 출구 연결 경로의 별도 개선은 이 변경에 포함하지 않았다.

### 받침 1.5cm + 추가 여유 2cm 재조정

콘 형상에 맞춰 받침 보정을 3cm에서 1.5cm로 줄이고, 받침 바깥 추가 여유는 1.5cm에서 2cm로 늘렸다. 원시 점과 예측 차체 사이 총 요구 간격은 4.5cm에서 3.5cm로 바뀐다. 출구 충돌검사는 같은 보정값을 쓰되 전환 상태 로직은 그대로다. 자동 후진은 추가하지 않았다.

`863714c` 대비 고정 위치 재생에서 기록된 콘 단계의 진행 제안은 `235135` 301/303, `235301` 307/307로 동일했고, 기존 진행이 정지로 바뀐 스캔은 없었다. 진행 제안의 원시 점 기준 최소 예측 간격은 각각 4.52→3.56cm, 4.55→3.78cm였다. 새 통과 성공이나 출구 동작을 실차로 검증한 결과는 아니다.

### 진입에만 먼 통로 후보 보조 탐색

부분 입구선을 사용한 `010910`, `011306`에서 콘 인계는 됐지만, 인계 직후 새 스캔의 통로가 `no_gate`로 탈락했다. 두 기록의 재생에서는 3.5cm 여유를 그대로 써도 1.15m보다 먼 콘 쌍이 전방 거리 상한에 걸렸다.

- 콘 제어 인계 뒤 첫 스캔부터 최대 8초·누적 odom 이동 0.40m 이내에만 적용한다. 유효 odom이 필요하며 유실(관측 시작 후)이나 점프로 닫힌 창은 같은 단계에서 다시 열리지 않는다.
- 새 일반 통로나 기존 odom 기억이 둘 다 없을 때만 뒤 차축 기준 전방 x가 1.15m 초과~1.40m인 후보를 평가한다. 먼 후보는 일반 경로 기억이나 직전 조향 이력에 저장하지 않는다.
- 이동 허가는 기존 20cm 차체 스윕, 라이다 관측, 안전 간격(받침 1.5cm + 여유 2cm), 목표 진행량 및 2회 연속 확인을 그대로 따른다. 차선 접근, 후진, 출구 충돌검사·전환 로직은 변경하지 않았다.
- `/mission/cone/timing`의 `entry_far_gate`는 먼 후보를 조향 탐색에 사용했음을 나타낸다. 자체로 진행을 의미하지 않으므로 `reason`, `speed`와 함께 확인한다.

`51bc15b` 대비 같은 위치와 기록 단계에서 비교한 콘 단계 전진 제안 수: `010910` 172→200, `011109` 206→206, `011204` 202→202, `011306` 128→187. 기존과 양쪽 모두 진행 명령이 나온 스캔에서 조향은 동일했고, 콘 단계 바깥 제안도 동일했다. 정지 중인 원본 자세를 재사용하므로 실제 통과·완주율을 뜻하지 않는다.

### 막힌 목표에 대한 2단계 전진 복구

보호 접근(M2 `approach`), 콘 추종(`cone`), 출구 연결(`exit_lane`)에서 일반 명령이 우선이다. 실제 관측된 콘 쌍 또는 신선하고 서로 일치하는 차선 경로·방향이 있고, 정상 방향의 원호가 충돌 여유를 만족하지 못할 때만 복구를 제안한다. 목표가 사라지거나 현재 차체 자체가 막힌 경우, 유효 스캔/odom이 없는 경우는 복구 대상이 아니다.

1. 직진 또는 차단된 방향의 반대 조향으로 짧은 전진을 가정한다. 첫 원호도 20cm(접근·콘)/40cm(출구)의 차체 스윕과 라이다 관측 조건을 통과해야 한다.
2. 그 위치에서 원래 목표로 다시 연결하는 전진 원호를 찾는다. 두 번째 원호도 같은 차체 모델과 여유(받침 1.5cm + 추가 여유 2cm)를 적용하고, 관측·진행량 및 차선 방향/거리 조건을 확인한다. 두 번째 원호는 계획 평가 전용이다.
3. 매니저는 같은 단계에서 일치하는 새 센서 제안 두 번과 최신 odom을 확인한 뒤 첫 움직임만 내보낸다. 10cm 물리 이동 목표 상한에 제동·지연 여유를 두기 위해 **odom 6.5cm 또는 0.65초 중 먼저 도달하는 시점**에 복구 명령을 끊는다. 센서 유실·후진 감지·ESTOP·조건 이탈에도 중단한다. 일반 검증 주행으로 15cm를 진행하기 전에는 반복 복구하지 않는다. 최대 실차 이동거리는 제동 상태와 함께 검증해야 한다.

복구는 `/mission/cone/recovery_cmd_vel`로 따로 보내며 M8 진입, 출구 완료 또는 일반 차선/콘 명령으로 승격하지 않는다. `/mission/cone/timing`의 `recovery_offered`, 매니저 로그의 `source=recovery reason=forward_recovery`를 실제 명령·odom과 함께 확인한다. 자동 후진과 기존 20/30/40cm 정상 충돌검사, 출구 전환 조건은 변경하지 않았다.

`8cf3393`과 네 bag의 기록 위치·단계를 재생했다. 일반 콘/접근/출구 제안은 동일했다. `010910`은 출구 복구 후보 한 건이 연속 확인에 실패했고, `011109`와 `011204`에는 실행 조건을 충족한 제안이 없었다. `011306`은 출구에서 새 후보 85건, 기록 시각 39.675초에 예산 게이트 통과 1회였다. 진입/콘 내부에서는 네 기록의 주된 문제가 `no_gate`여서 발동하지 않았으며, 접근·콘·출구 기하와 명령 게이트는 별도 테스트로 확인했다. 회귀 테스트 231개 통과. 재생 궤적은 원본 odom이며 실제로 새 궤적을 따라 이동하거나 출구를 완주했다는 뜻이 아니다.

시간은 **개발 Mac의 Python 코어** 기준이다. p95 약 4.6–8.0 ms, CPU 시간 p95 약 4.5–7.4 ms, 최대 wall time 약 36.7 ms였다. ROS 전송·다른 노드·Jetson 스케줄링 비용은 제외했다. GPU 추론은 없다. 실차는 `plan_ms/exit_ms/callback_ms/arrival_age_ms/output_age_ms`로 확인한다.

별도 단순 폐루프 시뮬레이션은 직선/좌우 곡선, 폭 0.60/0.72 m, 진입 각도/오프셋, ray 누락·잡음, 조향 변화율 제한을 조합했다. 점수 개선 전 21/24에서 개선 후 **24/24 완료, 충돌 0회**, 모델 받침까지 최소 여유 약 3.96 cm였다. 실제 마찰·조향·사각·받침 오차를 보장하지 않는다. 실차 90%/100% 성공으로 표기하지 않는다.

테스트는 계획기·원시 점 충돌·시간/odom 리셋·명령 인계·ESTOP·정지선과 기존 미션 회귀를 포함한다. 매니저 연결은 실제 M8Control을 가짜 ROS 메시지/전송으로 실행했다. 실제 DDS/launch/하드웨어 통합 검증은 별도로 필요하다.

조향 비교는 동일한 bridge 명령각 단위로 변환했다. 비교 가능한 움직임 샘플에서 기록 대비 절대 차이 중앙값은 auto_controll_02 약 4.62도, far_entry 약 7.91도, retest 약 13.11도다. 실패 주행/다른 제어기의 명령은 정답 조향이 아니므로 이를 그대로 모사하도록 튜닝하지 않았다. 성공 수동 기록 bag_cone_04에는 /limo/ack_cmd가 없어 정확한 명령각 차이를 계산하지 못한다. odom으로 추정한 곡률을 실제 조향 센서라고 대체 표기하지 않았다.

## 방법 선택과 출처

- [Coulter, Pure Pursuit (1992)](https://publications.ri.cmu.edu/implementation-of-the-pure-pursuit-path-tracking-algorithm): 관측 목표에서 곡률을 구하는 기하 추종. 목표 쌍이 잘못되면 추종도 잘못되므로 쌍 방향/폭을 함께 확인한다.
- [Regulated Pure Pursuit (2023)](https://arxiv.org/abs/2305.20026), [Nav2 공식 설명](https://api.nav2.org/nav2-rolling/html/md_nav2_regulated_pure_pursuit_controller_README.html): 속도/전방 충돌 규제 원칙 참고. 전체 Nav2 RPP를 이식한 것은 아니다.
- [Dynamic Window Approach (1997)](https://publications.ri.cmu.edu/the-dynamic-window-approach-to-collision-avoidance): 가까운 실행 후보 평가 원칙 참고. LIMO에서는 제자리 회전이 아니라 아커만 곡률만 사용한다.
- [F1TENTH Follow the Gap](https://github.com/f1tenth/f1tenth_lab4_template): 매우 가볍지만 가장 넓은 빈 공간이 콘 코스 바깥일 수 있어 이번에는 콘 쌍을 목표로 선택했다.
- [Mapless Local Trajectory Planning (2024)](https://arxiv.org/abs/2401.17732), [FaSTTUBe](https://github.com/papalotis/ft-fsd-path-planning): 경계/그래프 활용은 충분한 관측에서 유리하나 이번 입구의 희소 관측에서 완성 경로를 요구하는 부담을 피했다.
- [공개 LIMO URDF](https://raw.githubusercontent.com/agilexrobotics/limo_ros2/humble/limo_description/urdf/limo_ackerman.xacro), [LIMO Pro 문서](https://github.com/agilexrobotics/limo_pro_doc/blob/master/Limo%20Pro%20user%20manual%28EN%29.md): 명목 장착 참고. laser x=0.103와 rear axle x=-0.10 차이 0.203 m는 초기값이며 실제 Pro 장착 검증을 대체하지 않는다.

외부 코드를 복사하지 않았다. EKF는 관측 모델/공분산 확인 전 추가하지 않았다. 지금의 짧은 기억에는 odom SE(2) 변환이 더 가볍고 원인이 명확하다.

## 주요 설정

`params/m8.yaml`:

- speed=0.10: 현재 0 또는 0.10만 발행. 실제 못 움직이는 0.1 미만을 진행으로 취급하지 않는다.
- max_steer_angle=0.42, minimum_turn_radius_m=0.50: 안쪽 바퀴/차량 기하 기준, 기존 bridge 유지.
- vehicle_half_width_m=0.12, front=0.29, rear=0.09: 뒤 차축 기준 차체 외곽. 실제 치수 확인 필요.
- cone_padding_m=0.015, minimum_clearance_m=0.020: 콘 받침 한쪽 돌출 보정과 추가 여유. 출구 검사에도 적용하며 실제 받침이 더 넓으면 늘려야 한다.
- target_hold_sec=0.50, target_hold_distance_m=0.10: 최근 관측점 예측 상한.
- scan_timeout_sec=0.25, resume_scans=2: 오래된 명령 정지, 10 Hz일 때 복귀 확인 약 0.1초.
- motion_enabled=true: 통합 주행 기본 허용. 시험 launch는 기본 motion=false이며 실제 주행 시 명시적으로 true를 준다.

## LIMO 배포 — 일반 pull 대신 아래 사용

이력을 통합했으므로 기존 LIMO의 `git pull --ff-only`는 실패할 수 있다. 아래는 **로컬 수정이 있으면 중단**하고 기존 HEAD를 백업한다. reset --hard는 사용하지 않는다.

```bash
source ~/race_ws/install/setup.bash
m8_update() {
  cd ~/race_ws || return 1
  local m8_pkg m8_repo m8_backup
  m8_pkg=$(colcon list --packages-select jetracer_ros2 --paths-only) || return 1
  [ -n "$m8_pkg" ] || { echo "패키지 경로를 찾지 못함"; return 1; }
  m8_repo=$(git -C "$m8_pkg" rev-parse --show-toplevel) || return 1
  [ -z "$(git -C "$m8_repo" status --porcelain)" ] || {
    echo "로컬 수정이 있어 중단. 먼저 수정사항을 보존해 주세요."; return 1;
  }
  m8_backup="backup/m8-before-update-$(date +%Y%m%d_%H%M%S)"
  git -C "$m8_repo" branch "$m8_backup" || return 1
  git -C "$m8_repo" fetch origin || return 1
  git -C "$m8_repo" switch --detach origin/feature/m8-cone-corridor || return 1
  git -C "$m8_repo" branch -f feature/m8-cone-corridor origin/feature/m8-cone-corridor || return 1
  git -C "$m8_repo" switch feature/m8-cone-corridor || return 1
  git -C "$m8_repo" branch --set-upstream-to=origin/feature/m8-cone-corridor || return 1
  colcon build --symlink-install --packages-select jetracer_ros2 || return 1
  source ~/race_ws/install/setup.bash
}
m8_update
```

### 실행 — 하드웨어 한 번 + 미션 한 번

기존 all_in/매니저/콘/차선 실행을 종료한다. 이미 teleop 하드웨어가 살아 있으면 중복 실행하지 않는다. NoMachine에서:

터미널 1 — 하드웨어가 꺼져 있을 때만:

```bash
source ~/race_ws/install/setup.bash
ros2 launch jetracer_ros2 jetracer_teleop.launch.py
```

터미널 2 — 첫 정지선이 보이는 입구, 리모컨 코드 모드, 통로에 사람이 없는 상태:

```bash
source ~/race_ws/install/setup.bash
ros2 launch jetracer_ros2 m8_cone.launch.py motion:=true record:=true
```

차선·정지선·콘·매니저·bag 기록이 함께 실행된다. `~/bag_m8_local_날짜_시간`에 저장된다. 관측만은 motion:=false. 별도 bag record는 불필요하다. 차선 창에는 차선 제안이 표시되므로 실제 명령은 매니저 로그나 /cmd_vel로 확인한다.

### 실차 확인 목록

1. /cmd_vel 발행자는 매니저 하나, 구독은 기존 cmdvel_to_ackermann.
2. 아커만 모드 경고 없음, /scan 약 10 Hz, /odom 약 50 Hz.
3. 초반 `watch_entry`, 입구 검출 뒤 `preflight`까지 기존 M2 차선 명령. 전환 후 `approach`와 검사된 `source=lane`, 콘 획득 뒤 `phase=cone` 및 `source=cone`와 v=0.100.
4. safe_cmd_vel과 /cmd_vel의 v/omega 일치.
5. 멈추면 no_gate/path_blocked/footprint_blocked/stale_cone/exit_lane 중 정확한 이유.
6. 출구 선 뒤 새 차선 미검출이면 대기, 관측 차선이 생기면 인계.
7. Jetson plan_ms/exit_ms/callback_ms와 센서→출력 age 확인.

첫 시험은 리모컨으로 즉시 정지할 수 있게 저속 1회 수행한다. 실제 받침·차체 치수와 조향 반경 검증이 여전히 필요하다.

## 명령 시간초과와 복구 확인 이력 분리 (2026-11-16, 기준 29d6a23)

### 원인과 변경 범위

`020142`, `020242` bag에서 스캔 시각부터 콜백 진입까지 이미 약 100ms가
경과했고, 계획 계산·전달을 합치면 기존 250ms 유효시간을 넘는 경우가 있었다.
두 번째 bag에서는 복구 양수 제안이 29개 있었지만 실제 `forward_recovery`
출력은 없었다. 다음 제안을 받기 직전 이전 제안이 만료되면 확인 이력까지
초기화하여 서로 다른 두 관측을 연결하지 못하는 문제가 있었다.

- 클러스터 중심값을 한 스캔에서 한 번 계산한다. 선택 기준·후보 수는 그대로다.
- 결정론적인 원호 좌표만 읽기 전용 LRU(최대 256개)로 재사용한다.
  센서 점, 충돌 여유, 관측 여부와 주행 허용 결과는 캐시하지 않는다.
- 기존 점수에서 비음수가 보장된 선행 여유 벌점을 제외한 하한값이 이미
  검증된 최선 후보보다 나쁘면 해당 후보의 비싼 계산을 생략한다.
  실행할 후보에는 기존 충돌·관측·진행량 검사를 그대로 적용한다.
  점수식·동점 선택 순서·곡률 범위·20cm/출구 검사거리는 바꾸지 않았다.
- 복구의 **확인 이력**과 **현재 실행 가능한 명령**을 분리했다.
  타이머에서 제안이 만료돼도 확인 이력은 첫 관측 시각으로부터 최대 500ms만
  보관한다(두 원본 관측 사이 최대 250ms + 최신 명령 허용 지연 최대 250ms).
  현재 명령은 여전히 250ms 이내여야 하며, 반복된 동일 관측은 확인 횟수가 아니다.
- 실행 중 잠깐 만료되면 즉시 0을 출력한다. 원래 시작한 0.65초/6.5cm 예산을
  늘리거나 초기화하지 않고 그 안에서 신선한 동일 방향 제안이 오면 재개한다.
  명시적인 0/잘못된 제안, ESTOP, 단계 변경은 취소하며 odom 유실·후진도 차단한다.
  취소/소진 후 일반 주행 15cm로 재허용하는 기존 조건은 유지했다.
- 명령 유효시간 250ms, 충돌검사, 받침 1.5cm+마진 2cm, 0.10m/s 속도,
  후진 금지, 출구 전환 및 차선 대기 로직은 변경하지 않았다.

동일성 검사는 상태·목표점·속도·곡률·조향·최소 여유·복구 후보를 포함했다.
부동소수점 수치는 절대 오차 1e-10 이내로 비교했다. 검사 후보 생략으로
`candidate_count`는 감소하므로 이전과 같아야 하는 대상이 아니다.

동일한 **기록된 복구 제안/취소·타이머·odom 시간축**에서 첫 bag은 전후 모두
복구 출력 0회(목표 궤적 차단이 그대로임), 둘째는 0→5개 양수 출력 샘플이다.
44.326초에 시작하여 44.472초에 잠깐 재개하는 한 예산 구간이며, 취소 이후
다시 무제한 시도하지 않는다. 이것은 완주 5회나 실제 10cm 이동을 의미하지 않는다.
재생은 recorder 수신 시각을 노드 수신 시각의 근사로 사용하며 DDS 콜백 순서를
완전히 재현하지 못한다. 신규 출력 이후의 실제 차량 궤적도 시뮬레이션하지 않는다.

참고 민감도 계산: 개발 Mac의 스캔별 계산시간 비율을 기록된 Jetson `plan_ms`에
적용하면, 둘째 bag cone 단계에서 기하학상 tracking인 스캔의
`arrival_age_ms + plan_ms > 250ms` 횟수는 43→6으로 추정된다.
**이는 Jetson 재측정값도, /cmd_vel 정지 횟수도 아니다.** 센서/통신/카메라 경합과
출구 검사 비용은 별도이며 새 bag으로 전체 명령 연속성을 확인해야 한다.

회귀 테스트 242개 통과: 늦게 도착한 서로 다른 두 제안 확인, 만료 구간 무출력,
재개 시 예산 불변, 명시적 취소, 단계 변경, ESTOP, odom 유실, 초과 거리·시간,
읽기 전용 캐시와 현재 스캔 재검사를 포함한다. 개발 환경은 ROS2가 아닌 가짜
ROS 어댑터 테스트이므로 실차 검증을 대체하지 않는다.

다음 실차에서는 기존 launch/녹화 토픽 그대로 `plan_ms`, `candidate_count`,
`planning_result_stale`, `stale_cone`, `forward_recovery`, /cmd_vel 및 /odom을
함께 비교한다. 첫 bag의 18.6초 이후 path_blocked와 둘째 bag 출구 전환 대기는
이번 수정으로 해결했다고 판단하지 않는다. 진입 경로·속도·출구 정책은 별도 작업이다.
